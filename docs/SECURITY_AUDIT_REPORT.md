# Laporan Audit Keamanan & Bug Project Laravel ERP
**Tanggal Audit:** 2026-09-21
**Fokus:** Keamanan (Security), Logika Bisnis, Performa, dan Code Quality

---

### 🔴 1. KRITIS (Critical / Security Vulnerabilities)

#### A. IDOR (Insecure Direct Object Reference) pada Supplier Portal Isolation
**Temuan:**
Fungsi `$user->isVendor()` di model `User` diperiksa oleh `CheckPermission.php` untuk menolak vendor dari rute internal (staff). Namun, isolasi kebalikan (*reverse isolation*) untuk staf admin tidak diperiksa secara eksplisit di grup rute vendor di `routes/api.php`.
Staf internal juga terautentikasi (sanctum auth), dan jika *middleware* vendor saja yang jalan di blok tersebut dan hanya memuat vendor scope tanpa menolak staff secara ketat, ada kemungkinan *leaky query* bila kontroller portal vendor lupa mem-filter berdasarkan `$user->ven_id !== null`. Portal supply-chain data dapat diakses/dieksekusi tanpa pembatasan domain supplier.

#### B. Brute-Force & Credential Stuffing Risk di API Auth
**Temuan:**
Rute `/api/v1/auth/login` yang didefinisikan di `app/Http/Controllers/Api/AuthController.php` **tidak menggunakan proteksi throttle (Rate Limiting)**. API langsung merespons pesan *ValidationException* (`Username atau password salah.`).
Ini mengundang eksploitasi brute-force, dan karena algoritma *default hashing* Laravel (`BCRYPT_ROUNDS=12` di `.env.example`) cukup berat, puluhan/ratusan iterasi serangan bot dapat menyebabkan CPU *starvation* di server (Denial of Service).

---

### 🟠 2. TINGGI (High / Logic & Performance Issues)

#### A. Query Terbuka `searchable()` (Denial of Service by Query)
**Temuan:**
Di `app/Http/Controllers/Api/CrudController.php`, bila parameter `?q=` dikirimkan, loop atas kolom `$cols` akan menambahkan `.orWhere($col, 'like', "%{$q}%")`.
Pencarian dengan pola `%...%` (diawali wildcard) tidak dapat memanfaatkan *B-Tree index* di database. Untuk tabel berskala besar di sistem ERP (seperti transaksi dan log stok), query ini memaksa *Full Table Scan* yang ekstrem sehingga membebani resources I/O disk dan RAM secara massif bila banyak user melakukan hit berbarengan.

#### B. Kebocoran Performa saat `updated_at` Refresh Response
**Temuan:**
Di dalam `CrudController.php` pada fungsi `store()`, baris `$record->refresh()` dijalankan untuk mendapatkan nilai *autogenerated* dari tabel. Namun, bila `model` memiliki atribut tambahan (*appends*, relasi *eager-loaded*) yang terpicu ulang, prosedur standar ini dapat menimbulkan query beruntun yang tidak diantisipasi (N+1 Select issue) seketika *record* berhasil disimpan.

---

### 🟡 3. SEDANG (Medium / Data Integrity)

#### A. Kurangnya Mekanisme Batasan `per_page` yang Agresif
**Temuan:**
Pada logika di `CrudController.php`, nilai maksimal dari parameter `per_page` (*pagination*) adalah `200`. Untuk query di mana API juga melampirkan entitas terkait bersarang tinggi (*deep eager loading* dengan metode `$this->with()`), proses serialisasi 200 baris ke JSON per *request* dapat menaikkan lonjakan konsumsi memori tak terduga (*Memory Leak/Exhaustion*) secara instan pada proses *thread* PHP-FPM di server. Sebaiknya ukuran paginasi default diperkecil ke 10-25 dengan batas maksimal 50-100.

#### B. Password Policy (Kompleksitas) Terlalu Rendah
**Temuan:**
Model validasi password di `app/Http/Controllers/Api/AuthController.php` dan bagian administratif menggunakan rilis usang `['required', 'string', 'min:6', 'confirmed']`. Untuk aplikasi bisnis (ERP), panjang 6 karakter adalah risiko serius. Sertifikasi ISO 27001 dan best practice modern menuntut setidaknya panjang 8-12 karakter disertai campuran mode alfanumerik khusus.

---

### 🟢 4. RINGAN (Low / Housekeeping & Code Smell)

#### A. Kurangnya Type Hinting & Return Type pada Helper Relations
**Temuan:**
Banyak fungsi pembentuk relasi pada abstraksi Model (seperti `m_item.php`) tidak memiliki deklarasi *return type* khusus seperti `: HasMany` atau `: BelongsTo`. Walaupun secara *runtime* PHP berfungsi dengan baik, *type inference* menjadi kabur ("*mixed*") yang menghalangi deteksi cacat logika lebih dini dari modul *static analyzer* (PHPStan/Larastan). 

#### B. UI/UX: Format Pesan Alert pada CheckClientUuid
**Temuan:**
Di file `app/Http/Middleware/CheckClientUuid.php`, apabila transaksi dicegat dengan validasi *idempotent/duplicate*, pesannya berbunyi `"Operasi {$uuid} sudah pernah diproses."` Bagi operator fasilitas pabrik di lapangan, pesan semacam ini mungkin terasa problematis karena sistem seolah menyalahkan operator, meskipun fungsi aslinya mencegah penggandaan data (*double spend*) karena jaringan yang tidak stabil. Disarankan merubah kalimat ini dengan status konfirmasi halus *"Data sudah tersimpan (soft-retry)."* 

---

### Saran Tindakan Lanjutan (Action Plan):
1. **Proteksi Login:** Tambahkan *middleware* `throttle:5,1` pada rute auth.login.
2. **Isolasi Rute Eksternal:** Pastikan filter tipe aktor di `EnsureVendor.php` tidak sebatas pasif namun wajib mem-block tipe User yang berlevel internal.
3. **Database Guard:** Batasi filter `CrudController` agar tidak mengeksekusi parameter `?q=` jika kurang dari 3 huruf dan pasangkan index yang sesuai.
4. **Perkuat Keamanan Akun:** Upgrade konfigurasi *rules* validasi Password di seluruh endpoint registrasi/update.
